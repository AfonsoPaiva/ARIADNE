Ariadne Technical Reference Manual

An in-depth guide to Ariadne's internal mechanics, micro-allocation primitives, runtime bytecode instrumentation, reactive stream hooks, and distributed observability bridges.

1. Introduction & Motivation

In modern JVM systems, asynchronous programming models—including thread pools, CompletableFuture, Project Reactor, RxJava, and Java 21 Virtual Threads—introduce severe observability challenges. When an execution fails on a worker thread, standard JVM stack traces are severed at the async boundary. Developers are left with blind, truncated exceptions that show where the code crashed, but not who scheduled it or why it was called.

Ariadne solves this problem. It maintains a continuous causal record across threads with sub-microsecond overhead, reconstructing the full asynchronous ancestry only when an error actually occurs.

2. The Asynchronous Blind Spot Problem

When a method executes synchronously on a single JVM thread, the thread's call stack directly records the entire hierarchy of callers. If an exception is thrown, Throwable.fillInStackTrace() captures this call stack directly from the JVM frame pointers.

However, when execution crosses an asynchronous boundary (for example, submitting a Runnable to an ExecutorService or chaining a Mono.publishOn() in Reactor), the caller thread simply places a task descriptor onto a queue and returns immediately.

The Fundamental Dilemma

Traditional debuggers attempt to solve this by creating a new Throwable() on every single operator creation or scheduling call. Because 99.9% of tasks succeed, this generates massive object allocation, triggers heavy Garbage Collection pauses, and incurs a 10x to 100x throughput penalty. Consequently, tools like Reactor's Hooks.onOperatorDebug() are strictly prohibited in production.

3. Core Mechanical Architecture

Ariadne resolves this dilemma by decoupling causal tracking from stack trace synthesis:

  1. Scheduling Time (Happy Path): When a task is queued, Ariadne allocates a single immutable 40-byte pointer node (Link) in thread-local TLAB memory. Call sites are statically cached in a lock-free registry (SiteRegistry) with zero runtime object allocation during lookup (0 B).
  2. Execution Time: The worker thread attaches the Link to its active context for the duration of the task, ensuring nested asynchronous spawns inherit their parent.
  3. Failure Time (Exception Path): If an exception occurs, Ariadne walks the lightweight linked list backwards, queries the interned call-site registry, synthesizes an AsyncCausalityException, and attaches it via Throwable.addSuppressed().

4. The Lightweight Link Primitive (Exact 40 Bytes Footprint)

The foundational unit of Ariadne is the immutable io.ariadne.core.Link class. Its memory footprint is strictly calculated according to 64-bit JVM object layout specifications: 

public final class Link {
    public final Link parent;          // 4 bytes (Compressed OOPs) or 8 bytes
    public final int siteId;           // 4-byte integer index into SiteRegistry
    public final long threadId;        // 8-byte primitive caller thread identifier
    public final Object attachment;    // 4 bytes (Compressed OOPs) optional context payload (MDC)
    public final int depth;            // 4-byte integer for O(1) depth tracking and capping
}

Under a 64-bit HotSpot JVM with Compressed OOPs enabled (-XX:+UseCompressedOops, default for heaps < 32GB): the object header occupies 12 bytes, references 4 bytes each (parent: 4, attachment: 4), primitive int 4 bytes (siteId: 4, depth: 4), primitive long 8 bytes (threadId: 8). The total field payload is 24 bytes + 12 bytes header = 36 bytes. Applying HotSpot's 8-byte object alignment padding brings the exact instance footprint to 40 bytes. Without Compressed OOPs, it occupies 48 bytes.

Distinção Crucial entre Link e Hop Completo: O nó de dados fundamental Link consome estritamente 40 bytes em TLAB. Em um despacho assíncrono real via thread pool ou CompletableFuture, o overhead total medido é de ~230 B por hop, correspondente à soma do nó Link (40 B) com o wrapper de execução (AriadneRunnable / AriadneCallable ~32 B) e os objetos internos de continuação do JDK. Em contrapartida, soluções tradicionais que criam um Throwable a cada hop geram entre 1.500 B e 4.000 B por hop.

5. Lazy Backward Synthesis

When an exception escapes an instrumented task, AriadneReconstructor.enrich(Throwable) activates:

  • Traverses the Link hierarchy up to a configurable maximum depth (default: 32 hops).
  • Resolves each siteId to its class name, method name, file name, and line number from the SiteRegistry.
  • Constructs an AsyncCausalityException containing synthesized StackTraceElement frames mapping directly to originating call sites.
  • Appends contextual payloads (such as MDC diagnostic maps) to the exception message.
  • Attaches the synthesized cause to the original throwable using Throwable.addSuppressed(), preserving the original exception class and stack.

7. Zero-Code Java Agent

The ariadne-agent module is packaged as a standard Java Agent using ByteBuddy: 

java -javaagent:ariadne-agent-0.1.0-alpha.2.jar -jar application.jar

Upon JVM startup, the agent dynamically attaches byte-code advice to:

  • java.util.concurrent.Executor.execute(Runnable)
  • java.util.concurrent.ExecutorService.submit(Callable) and submit(Runnable)
  • java.util.concurrent.ScheduledExecutorService.schedule(...), scheduleAtFixedRate, and scheduleWithFixedDelay
  • java.util.concurrent.ForkJoinPool (via ExecutorService.execute(Runnable) / submit())
  • java.util.concurrent.CompletableFuture asynchronous supplier, action stages, and delayedExecutor.
  • Java 21 Thread.ofVirtual().start(Runnable) and Thread.startVirtualThread(Runnable).

The agent automatically checks for the presence of Project Reactor, RxJava, and SLF4J on the application classpath and installs the corresponding adapters without requiring configuration.

8. Reactive Framework Adapters

Project Reactor (ariadne-adapter-reactor)

Attaches to Reactor via Schedulers.onScheduleHook() and Hooks.onOperatorError(). When a task is scheduled on Schedulers.boundedElastic() or Schedulers.parallel(), the active Link is automatically captured and restored during subscription and emission.

RxJava 3 (ariadne-adapter-rxjava)

Utilizes RxJavaPlugins.setScheduleHandler() to wrap Runnable instances before they are dispatched to Schedulers.io() or Schedulers.computation().

9. SLF4J MDC Log Propagation

In distributed microservices, correlation identifiers such as traceId, spanId, and userId are placed in the SLF4J MDC (Mapped Diagnostic Context). Because MDC relies on ThreadLocal, switching threads causes all contextual logging data to vanish.

With ariadne-adapter-mdc:

  1. When AriadneContext.spawn() occurs, the adapter captures a snapshot via MDC.getCopyOfContextMap().
  2. When the worker thread executes the task, it binds the snapshot to the worker thread's MDC.
  3. When the task completes, it cleans up and restores the previous thread context, preventing thread-pool cross-contamination.

11. Java 21 Scoped Values & Loom Planned for v0.2.0

Roadmap Specification: This experimental carrier is designed for Java 21+ Scoped Values (JEP 446 / JEP 464).

In Java 21, millions of lightweight Virtual Threads can be created concurrently. Traditional ThreadLocal variables can create unexpected memory retention if not aggressively pruned.

Ariadne's planned ScopedValueContextCarrier will utilize JDK 21 java.lang.ScopedValue:

  • Values are immutable and bound strictly to lexical execution scopes.
  • Provides runWhere(Link, Runnable) and callWhere(Link, Callable).
  • Implemented dynamically via reflection so enterprise applications compile on standard Java 21 LTS without requiring --enable-preview.

Production Robustness & Safety Guarantees

1. Total Fail-Safe Guarantee

Every ByteBuddy advice method (CompletableFutureAdvice, ExecutorAdvice, ThreadAdvice), runtime wrapper (AriadneRunnable, AriadneCallable), and reconstructor method (AriadneReconstructor.enrich) is encapsulated in top-level try-catch (Throwable) blocks. Under no circumstances—including out-of-memory, classloading conflicts, or malicious tasks throwing during inspection—will Ariadne disrupt or crash the host application. If an exception occurs, the original user exception is preserved and re-thrown unaltered.

2. Data Leakage Prevention (MDC Allowlist)

Exceptions often end up in monitoring platforms (Sentry, Datadog, CloudWatch). Attaching raw MDC contexts risks leaking sensitive credentials (JWTs, session tokens, passwords, SSNs). Ariadne enforces:

  • Disabled by Default: Context attachments in exception messages are turned off by default (ariadne.exception.context.enabled=false).
  • Strict Allowlist: When enabled, only keys explicitly specified in ariadne.mdc.allowlist are rendered.
  • Bounded Footprint: Enforces a hard cap of 50 entries and truncates values exceeding 512 characters with ...[truncated] to prevent log flooding or OOM.

3. Chain Origin Preservation (Root Tradeoff in Sliding Window)

Standard FIFO sliding windows drop the oldest elements first when depth limits are reached. In web applications, the oldest hop is the HTTP Controller / ingress request handler—the single most important anchor for debugging. Ariadne implements root origin preservation:

  • The root origin hop (parent == null) is permanently pinned at the base of the chain.
  • The sliding window retains the most recent (maxDepth / 2 - 1) hops leading directly up to the error.
  • Tradeoff: Intermediate hops between the root origin and the sliding window are pruned, bounding memory to O(maxDepth) to prevent memory retention leaks in unbounded reactive streams while guaranteeing that both the root cause ingress and the immediate failure context are retained.

4. Spring Boot Startup Impact & Type Matcher Optimization

ByteBuddy's hasSuperType(Executor) inspects class hierarchies during loading. To prevent startup degradation in large frameworks (Spring Boot, Tomcat, Netty), Ariadne applies fast-path ignore matchers:

  • Skips framework internal bytecode: org.springframework.cglib.*, org.objectweb.asm.*.
  • Skips logging frameworks: ch.qos.logback.*, org.slf4j.*.
  • Evaluates dynamic class exclusion filter: AriadneConfig.isClassExcluded().
  • Empirical Startup Impact: On a standard Spring Boot application context (with @EnableAsync, ThreadPoolTaskExecutor, Reactor, and MDC), startup time was measured at ~10 to 13 ms, with negligible delta (< 5 ms overhead), proving zero startup friction in enterprise microservices.

15. Global Static State: Architecture & Operational Limitations

Para instrumentar o código de forma transparente sem poluir APIs corporativas, o Ariadne utiliza componentes estáticos de escopo global. É indispensável compreender o modelo de concorrência e as limitações inerentes a esse design:

1. Registro Global de Call Sites (SiteRegistry) e Segurança de ClassLoader

O SiteRegistry armazena metadados de pontos de chamada em mapas concorrentes estáticos (ConcurrentHashMap). Para assegurar imunidade contra vazamentos de memória (ClassLoader leaks) em servidores de aplicação (Tomcat, Jetty, WebLogic):

  • Desacoplamento de ClassLoader: A classe CallSiteMetadata armazena estritamente tipos primitivos e instâncias de String. Não mantém qualquer referência forte ou fraca a instâncias de Class<?> ou ClassLoader. O descarregamento de um WAR/EAR nunca é bloqueado pelo registro.
  • Coleta Automática via ClassValue: O cache ClassValue<Integer> aloca o ID diretamente na estrutura interna da classe alvo. Quando uma classe dinâmica ou lambda é coletada pelo Garbage Collector da JVM, sua entrada é purgada automaticamente sem intervenção.
  • Proteção contra Sobrecarga de Heap (Bounded Capacity): O registro é delimitado por -Dariadne.registry.max_sites (padrão: 65.536). Caso código dinâmico gere scripts ilimitados em loop, o registro degrada suavemente para ID genérico em vez de permitir crescimento irrestrito de heap.
  • Gestão Explícita de Ciclo de Vida: Disponibiliza SiteRegistry.clear() e SiteRegistry.size() para invocação em ServletContextListener.contextDestroyed() ou testes unitários.

2. Isolamento de Threads e Prevenção de Context Leaks (ThreadLocalContextCarrier)

O vínculo causal entre threads é propagado através de ThreadLocal. Em pools reutilizáveis de threads (como ForkJoinPool ou ThreadPoolExecutor), esquecer uma referência causaria poluição de contexto em tarefas posteriores. O Ariadne garante a integridade desse ciclo: todos os invólucros (AriadneRunnable, AriadneCallable) e advices do agente implementam try-finally obrigatório com attach() e close(), restaurando estritamente o estado original da thread.

3. Injeção no Bootstrap ClassLoader & Ambientes Multi-Tenant

Para que classes do núcleo do JDK (java.base, como CompletableFuture e ThreadPoolExecutor) possam invocar o motor de causalidade sem erros de ligação de módulos, o agente injeta o JAR do núcleo no Bootstrap ClassLoader search path via Instrumentation.appendToBootstrapClassLoaderSearch.

Implicação para Contêineres Corporativos (EAR / WAR / OSGi): Como as classes injetadas no bootstrap residem no nível mais alto da hierarquia de carregamento da JVM, seu estado estático é compartilhado entre todas as aplicações hospedadas na mesma JVM. Em servidores multi-tenant onde múltiplos WARs compartilham a mesma instância de JVM, as causas assíncronas são segregadas por thread/link individual, mas o registro de metadados é compartilhado a nível global.

4. Modos de Resolução de Call Sites e Custos Empíricos (CallSiteMode)

O Ariadne disponibiliza três estratégias de resolução de call site configuráveis via -Dariadne.callsite.mode=class | sampled:N | full (ou variável ARIADNE_CALLSITE_MODE) e alteráveis em tempo de execução via JMX (io.ariadne:type=Ariadne):

  • CLASS (Padrão, Recomendado para Produção): Utiliza ClassValue<Integer> para cachear o nome da classe do chamador a partir da classe do lambda/runnable (ex: PaymentService.lambda(PaymentService.java)). Latência medida: ~5.7 ns/op, com 0.0 B/op de alocação de memória (elimina completamente o uso de StackWalker no caminho crítico).
  • SAMPLED:N: Amostra 1 em cada N despachos com StackWalker completo para capturar método e linha exatos, atendendo os restantes via ClassValue. Para N=100: ~39.1 ns/op e ~9.7 B/op.
  • FULL: Executa StackWalker em cada despacho assíncrono para identificar o método e a linha exatos do chamador (ex: PaymentService.processPayment(PaymentService.java:16)). Latência: ~1.42 µs/op e ~960 B/op. Recomendado para ambientes de homologação, testes canário e depuração localizada.

16. Getting Started & Installation

Option A: Zero-Code Java Agent (Recommended)

Download ariadne-agent-0.1.0-alpha.2.jar from the GitHub Releases page and add the flag to your JVM startup script: 

java -javaagent:/path/to/ariadne-agent-0.1.0-alpha.2.jar -jar your-app.jar

<dependency>
    <groupId>io.github.afonsopaiva</groupId>
    <artifactId>ariadne-core</artifactId>

</dependency>
